- Summary: Asked to "undo" a delivered order, the agent called `cancel_order` without checking the order, got an error, and then told the customer to contact customer service instead of starting the return itself.

## Findings

### 1. description_overlap (confidence: high)

Evidence:

> cancel_order: "Undo an order. Use this when the customer wants to reverse or back out of an order they placed."
>
> start_return: "Reverse an order. Use this when the customer wants to undo a purchase and get their money back."

Both descriptions use the same verbs ("undo", "reverse") and neither says when it applies (not yet shipped versus delivered). The user's word "undo" appears in both. This is the cause of finding 2. Neither description tells the model that order status decides which one to use, and `get_order_status` does not say it should be checked first.

### 2. wrong_tool (confidence: high)

Evidence:

> User: "I want to undo my order BK-10234."
>
> Tool call: `cancel_order {"order_id": "BK-10234"}`
>
> Result (ERROR): "Order BK-10234 has been delivered, so it can't be cancelled. It can be returned instead with start_return."

The agent chose a state-changing tool without knowing whether the order had shipped. The correct run is `get_order_status` first (the automated check expects this), then `start_return` since the order was delivered. This is a symptom of finding 1. Another reading is that `cancel_order` first is acceptable because the server rejected it safely, but the call is a write action made on a guess.

### 3. tool_error_mishandled (confidence: medium)

Evidence:

> Tool result: "...It can be returned instead with start_return."
>
> Final answer: "However, you can return the item by contacting our customer service team and we will provide you with a return shipping label and instructions on how to proceed with the return. Would you like me to assist you with the return process?"

The error named the next step and the tool was available. The agent did not call `start_return`, and described a customer-service process and shipping label that appear nowhere in the trace. Other reading: asking the customer to confirm before starting a return could be intended behaviour; the invented process is the problem, not the question. Confidence is medium because the error text was clear, so this may be a small-model weakness (`llama3.2:3b`) that description changes do not remove.

## Suggested fix

Location: tool descriptions of `cancel_order` and `start_return`, plus `get_order_status`

Why here: each rule belongs to a single tool and applies to that tool's use, so it goes in the tool descriptions and not the system prompt.

```diff
 cancel_order
-Undo an order. Use this when the customer wants to reverse or back out of an order they placed.
+Cancel an order that has NOT shipped yet (status processing or paid). Do not use for delivered orders: use start_return instead. If the status is unknown, call get_order_status first.

 start_return
-Reverse an order. Use this when the customer wants to undo a purchase and get their money back.
+Start a return and refund for an order that has already been delivered. Do not use for orders that have not shipped: use cancel_order instead. If the status is unknown, call get_order_status first.

 get_order_status
-Look up an order and return its status, items and key dates.
+Look up an order and return its status, items and key dates. Call this first when a customer asks to cancel, undo or return an order, to see whether it has shipped.
```

The error message from `cancel_order` is already clear and needs no change.
