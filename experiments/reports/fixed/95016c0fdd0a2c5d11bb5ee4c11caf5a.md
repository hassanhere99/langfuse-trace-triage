## Findings

### 1. description_overlap (confidence: high)

Evidence:

> cancel_order: "Undo an order. Use this when the customer wants to reverse or back out of an order they placed."
>
> start_return: "Reverse an order. Use this when the customer wants to undo a purchase and get their money back."

Both descriptions use the same verbs ("undo", "reverse") and neither says when it applies. The user wrote "I want to undo my order BK-10234." and that matches both. Neither description mentions order status (not shipped versus delivered). This is the cause of finding 2.

### 2. wrong_tool (confidence: high)

Evidence:

> [generation 1] requested tool calls: cancel_order {"order_id": "BK-10234"}
>
> [tool result] {"error": "Order BK-10234 has been delivered, so it can't be cancelled. It can be returned instead with start_return."}

The agent called `cancel_order` without looking up the order. The order was delivered, so `start_return` was the right tool. A correct run is `get_order_status` first (as the automated check expects), then `start_return`. The failure is the symptom of finding 1. Another reading: the user's wording is ambiguous and the model reasonably guessed, but the description text gave it no way to tell.

### 3. tool_error_mishandled (confidence: high)

Evidence:

> [tool result] {"error": "Order BK-10234 has been delivered, so it can't be cancelled. It can be returned instead with start_return."}
>
> [final answer] "However, you can return the item by contacting our customer service team and we will provide you with a return shipping label and instructions on how to proceed with the return. Would you like me to assist you with the return process?"

The error was clear and named `start_return`. The agent did not call it. It told the user to contact customer service and described a shipping label process that appears nowhere in the trace. It then asked whether to help with a return it could have started itself. Nothing was claimed as done, so the user was not told the action succeeded, but they were sent away from the tool that could do the job. The error text was not vague, so the fix is not in the error message. This looks partly like a weakness of the small model (`llama3.2:3b`); I did not check whether another model behaves differently.

## Suggested fix

Location: tool description of `cancel_order` and `start_return`

Why here: the rule for when each tool applies belongs to the tools themselves, not the system prompt. Both descriptions need changing so that they are distinct.

```diff
 cancel_order
- Undo an order. Use this when the customer wants to reverse or back out of an order they placed.
+ Cancel an order that has not shipped yet. Check the order with get_order_status first. Do not use for delivered orders; use start_return for those.

 start_return
- Reverse an order. Use this when the customer wants to undo a purchase and get their money back.
+ Start a return for an order that has already been delivered, so the customer gets their money back. Do not use for orders that have not shipped; use cancel_order for those.
```

Finding 3 is not addressed by a text change here. The `cancel_order` error already names `start_return`. The second test below tracks it. If it keeps failing after the fix, the options are a different model or a regression test only.
