## Findings

### 1. description_overlap (confidence: high)

Evidence:

> cancel_order: "Undo an order. Use this when the customer wants to reverse or back out of an order they placed."
>
> start_return: "Reverse an order. Use this when the customer wants to undo a purchase and get their money back."

Both descriptions use the same verbs (undo, reverse) and neither says which order state it applies to (not yet shipped vs delivered). The user's word "undo" matches both. Neither description says to check the order status first, and `get_order_status` is not mentioned anywhere. This is the cause of finding 2.

### 2. wrong_tool (confidence: high)

Evidence:

> User: "I want to undo my order BK-10234."
>
> cancel_order {"order_id": "BK-10234"}
>
> Tool result (ERROR): {"error": "Order BK-10234 has been delivered, so it can't be cancelled. It can be returned instead with start_return."}

The order was delivered, so `cancel_order` was the wrong tool. A correct run looks up the order with `get_order_status` first (as the automated check expects), sees "delivered", then calls `start_return`. The user's message does not say whether the order had shipped, so a bare `cancel_order` call was a guess. This is a symptom of finding 1.

### 3. tool_error_mishandled (confidence: high)

Evidence:

> Tool error: "It can be returned instead with start_return."
>
> Final answer: "However, you can return the item by contacting our customer service team and we will provide you with a return shipping label and instructions on how to proceed with the return. Would you like me to assist you with the return process?"

The error named the next step, `start_return`, and the agent did not call it. It sent the customer to customer service and described a return-label process that appears nowhere in the trace. It then asked permission to "assist with the return process", although it had a tool for that. Other reading: asking for confirmation before starting a return may be acceptable behaviour, but the invented "contact customer service" instruction is not supported by any tool result. The error message was clear, so the cause is the model following the error badly (llama3.2:3b), made more likely because `start_return` is described only as "Reverse an order", which does not say it is the route for delivered orders.

## Suggested fix

Location: tool descriptions of `cancel_order` and `start_return`

Why here: The rule "cancel before shipping, return after delivery" belongs to these two tools, so it goes in their descriptions, not in the system prompt. Change both, not one.

```diff
 cancel_order
-  Undo an order. Use this when the customer wants to reverse or back out of an order they placed.
+  Cancel an order that has not shipped yet. Do not use for orders that are already delivered; use start_return for those. If you do not know whether the order has shipped, call get_order_status first.

 start_return
-  Reverse an order. Use this when the customer wants to undo a purchase and get their money back.
+  Start a return and refund for an order that has already been delivered. Do not use for orders that have not shipped; use cancel_order for those. If you do not know whether the order has been delivered, call get_order_status first.
```

Optional, lower priority: `get_order_status` could say "Use this first when a customer wants to cancel, undo or return an order and the order state is not known."
