- Summary: The customer's order number was rejected by `cancel_order` as invalid. The error did not say why, and the agent then told the customer the order could not be located. The order was not cancelled.

## Findings

### 1. tool_error_mishandled (confidence: high)

Evidence:

> tool result: `{"error": "Invalid order_id: \"10571\""}`
>
> final answer: "I apologize for the inconvenience, but I couldn't locate order 10571 in our system. Could you please provide the correct order number or confirm if you would like to cancel your current order?"

The tool said the ID is invalid, which is a format problem. The agent turned that into "couldn't locate order", which is a lookup problem. It then asked the customer for "the correct order number" without saying what a correct one looks like, and added "confirm if you would like to cancel your current order", which has nothing to do with the request. The error text carries no format or example, so the model had nothing better to say. The cause is the vague error message from the tool, not only the model's wording.

### 2. wrong_arguments (confidence: medium)

Evidence:

> user: "Please cancel order 10571."
>
> tool call: `cancel_order {"order_id": "10571"}`
>
> schema: `"order_id": {"type": "string", "description": "The order ID"}`

The agent copied the number exactly as the customer wrote it. The tool rejected that value, so the tool wants a different form. The schema says only "The order ID", with no format and no example, so this is an underspecified schema rather than a model slip. Related to finding 1: this is the first failure and finding 1 is what the customer saw.

Confidence is medium because the trace never shows the accepted format. Another reading is that the number is a well-formed ID of an order that does not exist and the server uses "Invalid" for that case too. The trace cannot separate the two. To settle it, check what `cancel_order` accepts: the validation rule on the server, or a successful `cancel_order` or `get_order_status` call from another run.

Not reported: `wrong_tool` and `description_overlap`. `cancel_order` was the right tool for "cancel order". The `cancel_order` and `start_return` descriptions do overlap ("Undo an order" / "Reverse an order"), but nothing in this trace depends on that.

## Suggested fix

Location: server behaviour (error message) of `cancel_order`, plus the `order_id` schema description. Because `get_order_status` and `start_return` take the same `order_id`, apply the same change to them.

Why here: the rule about what an order ID looks like belongs to the order tools, so it goes in their error text and schema, not in the system prompt.

I do not know the real order ID format, because the trace does not contain it. `<FORMAT>` and `<EXAMPLE>` below must be filled in from the order system, not guessed. If the server can map the bare number to a valid ID itself, doing that is the smaller change.

Server error message:

```diff
- {"error": "Invalid order_id: \"10571\""}
+ {"error": "Invalid order_id: \"10571\". Order IDs look like <EXAMPLE> (<FORMAT>). Ask the customer for the ID from their confirmation email; do not tell them the order does not exist."}
```

Schema:

```diff
- "order_id": {"type": "string", "description": "The order ID"}
+ "order_id": {"type": "string", "description": "The order ID, in the form <FORMAT>, for example <EXAMPLE>."}
```
