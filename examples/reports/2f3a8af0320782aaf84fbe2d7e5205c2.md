## Findings

Expected run: the user wrote "I don't want the book in order BK-10571 anymore, please start a return." Calling `start_return` with `order_id` = `BK-10571` matches the literal request, and it was made. When it fails because the order is processing, a correct reply tells the customer that a return is not possible yet, and offers (or makes) the `cancel_order` call, since an order that has not shipped is cancelled rather than returned.

### 1. tool_error_mishandled (confidence: medium)

Evidence:

> `start_return` `{"order_id": "BK-10571", "reason": "The book is no longer wanted"}` returned `{"error": "Order BK-10571 is not eligible for return because its status is processing."}`

> "As per our store policy, we can only initiate returns for orders that are in the shipped or delivered state."

> "Could you please contact our customer support team to discuss possible alternatives or a refund?"

The agent did not claim success and it repeated the status correctly. But the error contains no policy and no rule about "shipped or delivered". The agent made no `get_store_policy` call, so the "store policy" it cites was made up. It also did not try `cancel_order`, the tool that handles this case, and handed the customer to support instead. The error text says what failed but not what the customer can do next, so the model filled that gap itself.

Why medium: the trace shows the unsupported policy claim directly (no `get_store_policy` call anywhere). That the claim is wrong and that `cancel_order` would have worked comes from the demo agent's code, which is not part of the trace: `demo-agent/tools.py` has the returns policy "Returns can only be started for orders that have been delivered", the cancellations policy "An order can be cancelled only while its status is processing", and `start_return` rejects every status except delivered. Another reading is that a 3B model is simply unreliable at recovering from errors (`model_error`); the vague error message and the undifferentiated descriptions (finding 2) make the tool-side cause more actionable.

### 2. description_overlap (confidence: medium)

Evidence:

> `cancel_order`: "Undo an order. Use this when the customer wants to reverse or back out of an order they placed."

> `start_return`: "Reverse an order. Use this when the customer wants to undo a purchase and get their money back."

Both descriptions use the same verbs ("undo", "reverse") for the same situation, and neither says which order status it applies to. After the `start_return` error the model had no text telling it that a processing order belongs to `cancel_order`, which fits the missing pivot in finding 1.

`wrong_tool` is not reported: the user explicitly asked for a return and `start_return` was the literal match. Why medium: one trace is weak evidence of overlap on its own, and the model might have failed to pivot even with clear descriptions.

## Suggested fix

Location: server behaviour (error message) of `start_return`, plus the tool descriptions of `cancel_order` and `start_return`.

Why here: the rule "returns open after delivery, orders that have not shipped are cancelled" belongs to these two tools, not to every tool, so it does not go in the system prompt.

Server error message (`demo-agent/tools.py`, the `start_return` error), so the model is told what to do next:

```diff
- Order BK-10571 is not eligible for return because its status is processing.
+ Order BK-10571 is not eligible for return because its status is processing. Returns can be started after delivery. An order that has not shipped can be cancelled with cancel_order instead.
```

Tool descriptions, which is what the promptfoo test below checks (apply to `examples/promptfoo/tools.json`):

```diff
  cancel_order
- Undo an order. Use this when the customer wants to reverse or back out of an order they placed.
+ Cancel an order that has not shipped yet (status processing) and refund it. Use this when the customer no longer wants an order that is still processing, even if they call it a return. Does not work once the order has shipped or been delivered.

  start_return
- Reverse an order. Use this when the customer wants to undo a purchase and get their money back.
+ Start a return and refund for an order that has been delivered. Does not work for orders that are still processing or shipped; use cancel_order for orders that have not shipped.
```

The `start_return` wording is the same as in the report for trace dfd0865869ace75001ee6ce844dcb4d4. That report words `cancel_order` for the shipped-order case ("Orders that have shipped cannot be cancelled; ... a return can be started once the order is delivered"). The two `cancel_order` rewrites should be merged into one description before applying.
