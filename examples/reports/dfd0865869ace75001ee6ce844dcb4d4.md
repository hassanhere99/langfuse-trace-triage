## Findings

Expected run: the user wrote "Cancel order BK-10388, I changed my mind." A `cancel_order` call with `order_id` = `BK-10388` is right, and it was made. When it fails because the order has shipped, a correct reply says the order cannot be cancelled, makes no promise that a tool cannot keep, and does not claim any action was taken.

### 1. tool_error_mishandled (confidence: medium)

Evidence:

> `cancel_order` `{"order_id": "BK-10388"}` returned `{"error": "Order BK-10388 cannot be cancelled because its status is shipped."}`

> "If you would like to return the book, please let me know and I can provide you with a return shipping label."

The agent reported the error accurately, so it did not claim success. But it then offered a return and a return label. No tool in "Tools available" produces a return label for an order in this state, and the agent made no call to `start_return`, `get_order_status` or `get_store_policy` before making the offer. The error text only says what failed, not what the customer can do next, so the model filled that gap itself.

Why medium: the trace alone does not show that the offer is wrong. That comes from the demo agent's code, which is not part of the trace: `demo-agent/tools.py` has the cancellations policy text "after it is delivered the customer can start a return instead", the returns policy "Returns can only be started for orders that have been delivered", and `start_return` returns an error for a shipped order. On that basis, a return cannot be started for BK-10388 until it is delivered. Another reading is that the model simply invented a capability (`model_error`); the vague error message makes the tool-side cause the more actionable one, so it is reported here.

Not a finding, but related: `cancel_order` ("Undo an order. Use this when the customer wants to reverse or back out of an order they placed.") and `start_return` ("Reverse an order. Use this when the customer wants to undo a purchase and get their money back.") overlap, and neither says when it applies. In this trace the agent picked the tool the user's words asked for, so there is no wrong-tool pick and `description_overlap` is not reported. This trace is, however, a case where the missing "not once shipped" / "only after delivery" conditions matter.

## Suggested fix

Location: server behaviour (error message) of `cancel_order`, plus the tool descriptions of `cancel_order` and `start_return`.

Why here: the rule "shipped orders cannot be cancelled, and returns open only after delivery" belongs to these two tools, not to every tool, so it does not go in the system prompt.

Server error message (`demo-agent/tools.py`, the `cancel_order` error), so the model is told what to say next:

```diff
- Order BK-10388 cannot be cancelled because its status is shipped.
+ Order BK-10388 cannot be cancelled because its status is shipped. A return can be started after the order is delivered.
```

Tool descriptions, which is what the promptfoo test below checks (apply to `examples/promptfoo/tools.json`):

```diff
  cancel_order
- Undo an order. Use this when the customer wants to reverse or back out of an order they placed.
+ Cancel an order that has not shipped yet. Orders that have shipped cannot be cancelled; if this returns an error for that reason, tell the customer so, and say that a return can be started once the order is delivered. Do not offer a return or return label for a shipped order.

  start_return
- Reverse an order. Use this when the customer wants to undo a purchase and get their money back.
+ Start a return and refund for an order that has been delivered. Does not work for orders that are still processing or shipped; use cancel_order for orders that have not shipped.
```
