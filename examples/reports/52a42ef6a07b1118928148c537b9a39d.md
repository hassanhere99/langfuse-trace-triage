- Summary: The customer wrote "undo my order". Two tools both claim that request. The agent started a return straight away, without looking up the order, and told the customer a refund would follow.

## Findings

### 1. description_overlap (confidence: high)

Evidence:

> `cancel_order`: "Undo an order. Use this when the customer wants to reverse or back out of an order they placed."
>
> `start_return`: "Reverse an order. Use this when the customer wants to undo a purchase and get their money back."

Both descriptions use the same verbs ("undo", "reverse") and neither says when it applies. Nothing separates an order that has not shipped from one that has been delivered. The user wrote "undo", which matches both descriptions word for word. This is the cause of finding 2.

### 2. wrong_tool (confidence: medium)

Evidence:

> User: "I want to undo my order BK-10234."
>
> Generation 1 tool call: `start_return {"order_id": "BK-10234", "reason": "None"}`
>
> Tool result: `{"order_id": "BK-10234", "return_id": "RT-10234", "status": "return_started", ...}`

"Undo" can mean cancel or return, and which one is right depends on the order's state. The agent never called `get_order_status`, so it picked a state-changing tool without that information. The first call should have been `get_order_status` with `order_id` `BK-10234`.

Why medium: the trace has no order status, so it cannot show whether `start_return` was the wrong action in the end. The metadata `scenario_id: "undo_delivered_order"` is a label, not evidence about the order. If the order was delivered, `start_return` may have been the right action and the fault is that it was not checked. If it had not shipped, `cancel_order` was right.

### 3. wrong_arguments (confidence: high, low severity)

Evidence:

> `start_return {"order_id": "BK-10234", "reason": "None"}`
>
> Tool result: `"reason": "None"`

The user gave no reason. The schema describes `reason` as "Why the customer wants to return the order." and does not say to leave it out when unknown. The model filled in the string "None", and the tool stored it. The cause is the underspecified schema, not a model slip.

### 4. missing_tool_call (confidence: medium)

Evidence:

> Final answer: "Once we receive the item, we'll process a full refund to the original payment method."

The tool result only says "A prepaid return label has been emailed to the customer." It says nothing about a refund or the payment method. That claim comes from the model, not from any tool. `get_store_policy` (topic `returns`) could have supplied it, and it was not called.

Why medium: the claim may match the real policy. The trace cannot confirm it.

## Suggested fix

Location: tool description of `cancel_order` and `start_return` (both), and the schema description of `start_return.reason`.

Why here: the rule for when each tool applies belongs to the tool, not to the system prompt. The overlap is between two descriptions, so changing only one would leave the other claiming the same request.

```diff
 cancel_order description
- Undo an order. Use this when the customer wants to reverse or back out of an order they placed.
+ Cancel an order that has not shipped yet (status "processing" or "paid"). Do not use for orders that have shipped or been delivered; use start_return for those. If you do not know the order's status, call get_order_status first.

 start_return description
- Reverse an order. Use this when the customer wants to undo a purchase and get their money back.
+ Start a return for an order that has already shipped or been delivered. Do not use for orders that have not shipped; use cancel_order for those. If you do not know the order's status, call get_order_status first.

 start_return.reason description
- Why the customer wants to return the order.
+ Why the customer wants to return the order, in the customer's words. Omit this field if the customer has not said.
```

Also worth doing on the server (not checked against the code base, since it is not in the trace): `cancel_order` should reject shipped orders and `start_return` should reject unshipped ones, with an error that names the other tool. That stops a wrong pick from changing state even when the description is read wrongly.

Finding 4 is not covered by this diff. If it recurs, say in the `start_return` result or its description that the refund is handled after the item arrives and that the agent should not state refund terms, or tell the agent to use `get_store_policy` for them.
